# VideoSieve 单机重做方案

日期：2026-09-20。状态：架构方向已采纳，代码迁移尚未完成。

用户已确认部署范围：一台电脑或服务器，个人／少量用户使用。
本次核查基于代码和配置，未启动服务、运行模型或执行端到端测试。

## 1. 结论与边界

采用 **Next.js + FastAPI + SQLite + 独立 Python worker + 本地工作区**，
不引入 Celery、Redis 或通用工作流引擎。

Celery 是将任务交给 worker 执行的任务队列框架；Redis 在旧规划中承担消息中转
和事件通道。当前需求没有体现多机扩容的必要性。SQLite 可以承担队列、状态和
事件的持久化；实际计算仍由 Python worker、FFmpeg 和模型执行。

首版一个 worker 实例，一次执行一个视频任务；允许多个任务排队和同时查看。
画面摘要使用受限并发，GPU 推理默认串行。资源与实测允许后再增加视频并发。
API 与 worker 分进程，API 重启不应杀死正在运行的计算任务。

数据库位于同一主机的本地磁盘。远程用户通过 HTTP 访问应用，不直接访问数据库。
若以后需要多个计算节点、高写入并发或高可用，再评估服务端数据库与消息队列。

## 2. 核查到的实际问题

| 问题 | 代码证据 | 影响 |
| --- | --- | --- |
| 每个任务创建 API 守护线程 | `apps/api/service.py::_default_job_dispatcher` | 缺少持久队列领取和可靠的进程重启恢复 |
| Redis 仅有内存实现 | `packages/infra/event_bus.py` | live 方法未实现，内存通知不是可恢复的事件记录 |
| 最终摘要拼接前三个非空片段 | `packages/deliverables/service.py::_render_summary_text` | 没有全文总结模型调用 |
| 整理稿只是逐段输出原文 | `packages/deliverables/service.py::_render_clean_transcript` | 尚未实现去口语与结构化改写 |
| ASR 默认或未知 provider 都落入模拟实现 | `packages/asr/factory.py` | 漏配、拼写错误也可能产出看似成功的假转写 |
| 画面摘要缺密钥、网络错误、无效或空响应回退占位文本 | `packages/frame_summary/service.py` | 调用失败可能仍写出结果并标记阶段成功 |
| 控制面与执行器状态不一致 | `apps/api/service.py::_default_control_dispatcher`、`packages/pipeline/orchestrator.py::_safety_point` | API 的 pause 写数据库，执行器却依赖实例内 pending pause；需验证实际停止行为 |
| 配置快照未全面约束执行 | `packages/pipeline/orchestrator.py::_read_vlm_str` / `_read_vlm_int` | VLM 阶段读取可变系统设置，与快照承诺不一致 |
| checkpoint 不等于自动恢复 | `packages/pipeline/orchestrator.py::run_job` | 有文件和显式起始阶段参数，但不能据此宣称崩溃后自动跳过已完成工作 |
| 环境与能力描述失真 | 旧 `AGENTS.md`、`CLAUDE.md`、`README.md` | 无骨架、Celery、conda、Python 3.11 安装指令与当前仓库不一致 |

保留并校验已有的视频接入、关键帧算法、FunASR 适配、工作区约定和前端基础。
测试中允许 mock；真实运行不得自动切入 mock。现有单测文件存在不等于真实视频验收通过。

## 3. 单机执行架构

```text
浏览器 ──HTTP / WebSocket── FastAPI
                              │
                         SQLite（本地）
                              │
                       Python worker
                              │
                   FFmpeg / ASR / VLM / LLM
                              │
                        workspace 文件
```

- API：校验配置、创建任务、记录控制请求、提供快照和产物下载。
- SQLite：保存队列、实际状态、控制意图、阶段进度、执行记录和事件。
- worker：轮询队列、领取任务、执行阶段、更新状态与检查控制请求。
- 文件系统：保存视频、音频、原始转写、关键帧和生成结果；数据库保存引用。
- WebSocket 沿用现有前端通道。API 按事件游标批量读取 SQLite 后推送；
  内存通知最多用于加速，不承担可靠性。无需另换 SSE 才能移除 Redis。

### 3.1 最小持久化模型

在现有 projects/jobs/settings 基础上，通过版本化迁移补齐：

- `jobs`：排队顺序、实际状态、期望动作、配置快照、当前执行标识、重试时间。
- `job_stages`：阶段状态、输入指纹、尝试次数、错误、进度和输出引用。
- `job_attempts`：worker 身份、开始时间、心跳、结束原因，关联一次执行。
- `job_events`：单调递增 ID、job、事件类型、必要内容与时间，用于恢复和追踪。
- `artifacts`：产物类型、路径、校验信息、来源阶段及所属执行。

详细日志可继续写文件；必要事件落库。进度限频合并，事件和日志设置保留策略。
不把每一帧的高频数据都写成数据库事件。

### 3.2 领取、事务与恢复

1. 创建任务并持久化成功后才返回“已入队”。worker 定期检查队列。
2. 用短事务原子领取（例如 `BEGIN IMMEDIATE` 加条件更新），避免重复领取。
3. 使用 WAL、连接级外键检查、合理的 busy timeout；各执行上下文使用独立连接。
   视频解码、下载、模型调用均发生在事务之外。
4. 首版使用 OS 级单实例锁限制 worker，心跳仅表示可疑失联；不能仅凭超时就
   再派发仍可能运行的任务。确认旧执行及子进程退出后，才能恢复或重试。
5. worker 崩溃后的任务标记为 interrupted 并给出恢复入口，排队任务保留。
   已有成功阶段只有在输入/配置指纹及产物校验匹配时才可复用。
6. 产物先写执行专属临时路径，完整写入后原子发布，再提交数据库产物引用与
   阶段成功事件。启动恢复时处理“文件已发布但数据库未提交”的窗口。
7. 外部模型调用不承诺 exactly-once；响应返回前后发生崩溃可能导致重复调用和费用。
   保存已确认的分块结果，并在恢复时说明不确定的调用。

### 3.3 控制语义

- 暂停：先保存 pause 请求并展示“正在暂停”；worker 在可中断点保存进度并退出
  当前任务后，才报告 paused。不能把改数据库状态当作暂停成功。
- 继续：重新入队，由 worker 从已验证的阶段／分块边界恢复。
- 取消：保存 cancel 请求，停止后续调用，清理受管理的子进程后确认 cancelled。
- 删除：先确认执行停止，再清理产物与记录；保留失败重试状态，不在写入中删除。
- 模型调用和本地推理可能无法瞬间中断；UI 显示等待边界或超时，不能假报停止。
  不可中断的本地工作如需强制终止，应隔离在受管理的子进程内并处理其进程树。

## 4. 让模型产物真实可信

### 4.1 三种能力分别配置

| 能力 | 首版建议 | 缺失或失败的行为 |
| --- | --- | --- |
| ASR | 明确选择真实本地 FunASR；保留接口以便以后接云服务 | 未知 provider 拒绝；模型/依赖加载失败显示原因；禁止返回 mock |
| Frame Summary | 视觉输入模型，复用已有兼容接口 | 缺密钥、超时、鉴权失败、空内容等分类报错；不写占位摘要 |
| Overall Summary | 独立 LLM 配置，首版输入转写和画面描述文本 | 必须实际调用模型并校验结果；不以截取或拼接冒充总结 |

创建任务时校验选中能力所需配置；运行时再处理网络和模型可用性。
模型准备和加载进度应可见，不在 API 启动时无提示地下载大模型。
mock 通过测试依赖注入提供，生产默认值与错误分支不能选择 mock。
媒体准备需验证音轨、采样率、时长和可解码性，明确生成模型需要的音频，避免
仅因文件扩展名正确就送入 ASR。验收同时核对转写内容和时间戳。

用户未选的阶段明确记为 skipped。选中的必要阶段失败，任务不能标为全部成功；
已完成的原始转写、关键帧等仍可查看。可选阶段降级必须显式约定并展示缺失项。

### 4.2 摘要与笔记生成链路

1. 保留原始转写和时间戳，模型改写另存，二者在界面中清楚区分。
2. 将转写与对应关键帧描述按时间区间组织为可追溯材料。
3. 短视频在上下文预算内直接总结；长视频按预算切分，先生成带来源引用的
   分段摘要，再汇总为全文结构、结论和摘要。记录所有分段的覆盖情况。
4. 将文字整理、图文笔记、最终摘要作为明确的模型生成步骤。
   `deliverables` 负责格式化、引用回填与导出，不能隐含模拟总结逻辑。
5. 保存模型名、提示词版本、非敏感参数、输入指纹及调用结果，支持单阶段重试。
   检查引用是否存在；文本忠实度与覆盖率仍需真实视频人工抽查。

按能力定义简单依赖：图片摘要需要关键帧；全文摘要需要至少一类有效内容。
首版全文摘要消费文本和画面描述，不要求再次传入全部原图；原图增强另行评估。
重跑上游阶段时使受影响的下游结果失效，不误用旧总结。

## 5. 配置与文档收敛

- Python 统一 uv、锁文件及 `.python-version`，当前 pin 为 3.12；前端遵循 npm 锁文件。
- 本地 ASR 依赖目前在主依赖中，`asr_local` extra 为空。重做时再决定是否真正拆分
  GPU/本地模型依赖，不能用空 extra 宣称已做可选安装。
- 部署配置、系统设置、任务快照分层。创建任务冻结模型、提示词和参数，执行阶段
  读取快照；密钥以受保护的配置/引用取得，不写入普通快照与日志。
- 更新 AGENTS、CLAUDE、README、运行说明中的已知事实；旧架构明确标识其规划性质。
- [ADR-0005](../adr/ADR-0005-single-host-sqlite-worker.md) 已替代 Redis/Celery 目标；
  实现新调度器时继续同步架构、状态机、事件、配置、worker 与部署文档。历史规划
  保留可追溯，不批量删除旧资料。
- 单独核对前端依赖与 lint 配置、Python 打包范围、FFmpeg/ffprobe 等外部依赖，
  用实际启动与构建结果确定受支持的版本组合。

## 6. 分阶段实施与验收

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 | 固化现状、补迁移与备份方案、纠正文档 | 区分真实能力、mock、未实现能力；保留已有数据 |
| P1 | 移除生产静默 mock/占位降级，建立三类模型配置及真实总结步骤 | 真实视频得到真实转写、画面描述和总结；漏配/失败明确可见 |
| P2 | SQLite 持久队列、独立 worker、事件恢复和控制语义 | API 重启任务继续；worker 崩溃可识别恢复；重复领取、暂停、取消与删除经过验证 |
| P3 | 长视频分段总结、断点复用、产物预览和依赖开关 | 全视频覆盖、来源可追溯、改配置不影响已建任务、不重复处理已确认分块 |
| P4 | 环境复现、质量检查、文档与 UI 收尾 | 在目标 Windows/Linux 环境复现安装和运行，文档列明实际验证情况 |

单测关注真实边界：错误响应不能成功、多个领取者不能拿到同一任务、未停止不能
被标记暂停、恢复不复用损坏产物、摘要覆盖后半段内容。集成验收至少包括本地视频、
B 站输入、真实本地 ASR、真实 VLM/LLM、超时/鉴权失败，以及执行中重启。
外部调用的费用、时长和人工质量抽查结果随验收记录；未执行不能标记通过。

## 7. 选型依据

- [Celery 官方介绍](https://docs.celeryq.dev/en/stable/getting-started/introduction.html)：
  任务队列、broker、worker 与分布式运行；官方不支持 Microsoft Windows。
- [SQLite 适用场景](https://www.sqlite.org/whentouse.html)：本地应用、低至中等流量服务，
  同时写入者受限。
- [SQLite WAL](https://www.sqlite.org/wal.html)：读写可并行，但同一时刻只有一个写者；
  WAL 要求共享数据库的进程位于同一主机，不适合放在网络文件系统供多机访问。
- [SQLite 事务](https://www.sqlite.org/lang_transaction.html)：短写事务与 IMMEDIATE 事务行为。

以上能力限制来自官方资料；SQLite 队列加独立 worker 是基于本项目单机范围的设计判断。
